## Search diagnosis and Atlas control

The standard configuration has Atlas disabled. Static startup locked after
15.374 input seconds (40.03 CPU seconds). The five observed search results spent
11.759 of 15.278 summed wall seconds preparing registration targets, about 77%.
There were 38 preparations, zero cache hits and 42 alignment calls. Descriptor
work was only 89 ms. Moving search similarly spent about 80% of observed search
wall time on target preparation. Cache counters locate repeated preparation;
they do not by themselves identify the precise eviction/key-change cause.

Using the existing precomputed Atlas, with the same input, four cores and
acceptance settings, static lock took **1.936 input seconds and 5.20 CPU seconds**.
Total process-to-lock time is separately recorded in JSON, including map loading.
Both runs selected keyframe 0. Final published positions differed by 5.93 mm and
orientations by 0.292 degrees. This is same-map consistency, not proof of equal
independent accuracy. No default or acceptance threshold was changed.

The uncontended result is `n3_static_atlas02`. The earlier Atlas pilot overlapped
artifact compression and is retained only as additional functional evidence.
The experiment reduces total search computation substantially, but **does not
meet a half-core search average** and raises the one-second search peak. Atlas
adoption on other maps and independent real-sensor routes needs its own check.
The cache is about 77 MiB on disk; its compilation was performed on the x86 host,
so its compile timings are not board performance figures.

Moving startup did not lock within the 59.9 s input window. Three logged attempts
were rejected by directional visibility, with support about 0.393, 0.342 and
0.451; another failed likelihood/margin/convergence requirements. The derived
clouds retain an earlier acquisition's visibility instead of fresh rays at the
synthetic viewpoint. These results do not justify weakening a reliability gate.

## Switching, persistence and regression

The ARM64 core regression passed 3/3 targets: `test_map_extension_route`,
`test_graph_solver_execution`, and `test_point_cloud_matcher`, in 5.69 s.
The full Humble/Noetic x86 suites are recorded in the handoff evidence.

The native ROS doorway E2E passed switching, motion, save and reload. The service
completed in 27.89 ms, with no process restart or additional lock. Extension and
reload maxima were both 0.305 mm in this synthetic fixture.

On the 250-keyframe input, the node locked, tracked for ten seconds, then accepted
`start_map_extension`. Service completion took 1.026 s while live output
continued; the largest observed receive gap within one second of the switch was
31.36 ms. The projection session stayed unchanged and the lock count remained
one. Static extension ran for another 34 s and saved map, PCD and Atlas artifacts.
This does not establish long-duration moving-extension resource bounds.

Fresh processes successfully loaded the saved mapping and extension maps with
their generated Atlases and localized once each. The first small-map reload
check mistakenly used the original map's static location rather than the
separate route used to build that partial map. It did not lock and is retained
as `reload_mapping`; `reload_mapping02` uses the actual mapping route's middle
observation and passes. `reload_handoff` passes using the original static input.

An initial FAST-LIO probe also stopped before replay because an output-connection
check used ROS 1's method on a ROS 2 subscription. Only the copied test harness
was adapted; the original probe and failed output are retained. The successful
measurement is `fastlio02`.

### What the measurements prioritize

The large-map half-core target remains unmet in both initial search and normal
native tracking. The small-map two-second result does not generalize to this
larger map. Thread-count changes alone do not remove the measured work.

Loader inspection identifies a precomputation opportunity, not a proven duplicate
that can simply be deleted: `MapSerializer` rebuilds causal-submap RHPD and heading
descriptors, while the Atlas currently restores single-frame place descriptors
and the place catalog. Retrieval still reads the rebuilt submap and heading
information. Any cache extension must preserve those inputs and map/configuration
binding. Their individual share of the 14 s core load has not yet been isolated.

The next optimization targets are initial/recovery geometry and visibility,
remaining map-load preparation, and the native global-cloud preparation/storage
cost. Broader live-sensor and longer moving-extension tests remain separate work.
Raw scripts, complete outputs, negative controls and input hashes are retained
under `build/n3mapping/rk3588_20261028/followup`. Results are recorded here rather
than added to the public README. No runtime algorithm, acceptance threshold,
installed binary, navigation frozen library or deployment default changed.

This stage optimizes map preparation without changing candidate admission,

workers; x86 validation uses CPUs 0,2,4,6. Native ROS inputs run at 1×. The source
base is `0d8b5c4`; the implementation is committed locally as `1a8a9aa`

### Why startup was slow

The initial **x86** phase probe measured 5.15 s for core loading: 3.33 s rebuilding
causal-submap RHPD/heading features, 1.55 s loading Atlas, 0.23 s reading and
validating the map, and 0.03 s restoring the graph. These are not RK3588 timings.
The preceding **RK3588** core load was 13.78–13.90 s; native node readiness was
19.61–20.53 s, including visualization preparation and ROS startup. The later
paired native controls below have their own measured baseline, not a substituted
x86 denominator.

Atlas compilation already computes submap and heading features for its place
catalog but previously discarded them. The new cache persists those results,
bound to the source map and descriptor configuration. Core loading restores
these after Atlas validation. Standalone map loading, v2 caches missing these
fields, and changed descriptor parameters rebuild from point clouds. Damaged
matching caches are rejected. Load logs now identify read, parse, keyframe/submap,
descriptor and graph phases; descriptor restoration reports cached counts.

Atlas v3 omits the nine matrix elements per point only when the target already
uses the normal-derived fixed-spectrum covariance model. Point coordinates,
normals and explicit nonstandard covariance matrices are preserved. The reader
accepts v2 and v3; the geometry/config fingerprint is unchanged. The v3 compiler
output is **311,694,939 bytes (297.26 MiB)**, versus the original
626,874,615 bytes (597.83 MiB). The descriptor-cache-only v2 ablation is
659,999,196 bytes (629.42 MiB). Old binaries require their original v2 Atlas;
comparison artifacts were written to new paths, not over the old sidecars.

Both adapters now construct the visualization cloud only when a subscriber
appears. They use keyframe revisions and the same shared map-artifact module;
Humble no longer substitutes an unbound adjacent PCD. The middleware retains the
latched/transient-local message, so the node no longer retains an additional
PointCloud2 copy. An unchanged global-map revision also bypasses cache sorting.
Extension/pose revisions still rebuild the cloud. This does not remove the
first visualization build when a subscriber actually needs it.

### Transport, harness and deployment record

The first container controls used Docker's default 64 MiB shared-memory
filesystem. That could not host the configured per-participant DDS segments and
reported SHM initialization failure. Those pilot runs are excluded; the paired
controls were repeated with `--shm-size=512m`. The XML segment size remains
64 MiB. Full-node observer and backend use the same profile and isolated domain.
A stale pre-extension x86 probe also failed because its core class layout did
not match the newer library; it was rebuilt against current headers before all
accepted replays. Noetic's older CTest ignored `--test-dir`; the accepted 67-test
run executes from the actual build directory.

The authorized Humble launch default now selects `config/fastdds.xml` (64 MiB SHM
and ordinary UDP) only when an operator profile is absent. Explicit `dds_profile`
and existing DDS/RMW/domain/localhost settings remain respected. Twelve launch
environment checks pass. Native launch E2E passes with both the explicit local
profile and the new default. Two independent local ROS 2 processes deliver all
40 ordered 1,280,145-byte serialized point-cloud messages with matching payload
hashes. This validates local transport; no multi-host RViz qualification is
claimed. No FAST-LIVO2 fork/runtime was changed. The reusable deployment guidance,
including container capacity and the distinction from C++ algorithm code, is in
[logging and DDS setup](../logging.md#launch-configuration-and-docker-capacity).
